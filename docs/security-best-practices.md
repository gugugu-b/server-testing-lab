# 安全笔记

这篇有点特殊。我自己在这个工作区里踩了不少明文凭据的坑，所以记下来，主要是提醒自己别再犯。

> 这不是给外部看的规范，是我的自查清单。

---

## 为什么最怕 BMC

BMC 是独立于 OS 的管理控制器——**OS 没起来、系统崩了，它照样能上下电、刷固件、做控制台重定向**。

也就是说 **BMC 被打穿 = 整机沦陷，而且攻击者根本不用碰 OS**。测试环境带外常常开着默认口令，这个风险一直摆在那。

## 我踩过的坑

### 1. 口令写在脚本里

```python
# ✗ 我曾经这么写
server_password = "********"
iperf_server_username = "root"
dpu_passwd = "********"
```

问题在于：脚本会被复制来复制去，改一个文件要同时改十个地方；而且这些文件迟早会被打包发出去。

现在我的做法是**配置文件和脚本分开，配置文件权限 600**：

```bash
chmod 600 /etc/testlab/credentials.env
chown root:root /etc/testlab/credentials.env
```

脚本里只读变量，不存值。

### 2. 口令写在命令行

```bash
# ✗ 这条会进 shell history，ps 也能看到
ipmitool -I lanplus -H <IP> -U Admin -P ********
```

```bash
# ✓ 交互输入，或者用环境变量
ipmitool -I lanplus -H <BMC_IP> -U <user> sel list
export IPMI_PASSWORD='********'
ipmitool -I lanplus -H <BMC_IP> -U <user> sel list
unset IPMI_PASSWORD
```

### 3. 口令写进笔记

这个是我最亏的一次。我把内部 wiki、AC Server、BMC、OS root 的口令都记在笔记本里，然后那份笔记进了同步目录。

**只要进过版本库或者发出去过，就必须当作已经泄露。**

现在我的规矩：

- 口令一律放公司口令管理工具，笔记里**只写"在哪儿取"**
- 个人笔记不进任何代码仓库
- 提交前自查：口令、Token、密钥、内网 IP、拓扑

### 4. 令牌比口令还危险

我笔记里还出现过 GitHub PAT 和钉钉机器人 token。这两个比口令麻烦——口令改了事，**令牌是长期有效的**，泄漏了别人能直接用你的身份干事情。

**现在我的检查清单里有一条：长 hex 串、PAT 前缀、token 字段，一律当作凭据处理。**

### 5. `.gitignore` 救不了已经提交的

```gitignore
*.env
*secret*
*.key
*.pem
id_rsa*
logs/
*.log
```

但要清楚：**`.gitignore` 只对还没进版本库的文件生效**。已经提交过的，光删文件没用——

**必须假定凭据已经泄露，直接去吊销、轮换。** 这不是可选项。

## 脱敏占位符规范

这个工作区已经全量脱敏过了，统一用 `【已脱敏:xxx】` `【内网:xxx】`。

**为什么用全角 `【】` 而不是 `<>`**：

```bash
# 半角会直接把脚本写废
RemoteOS_password=<已脱敏:PWD>
# bash 把 < 理解成输入重定向，语法直接报错
```

全角括号在 bash、Python、CSV、Markdown 里都是安全的字符。

## BMC 这块我一般这么管

| 项 | 我的做法 |
| --- | --- |
| 默认账号 | 上电就改或者直接禁用，不留出厂口令 |
| 口令强度 | ≥12 位，大小写+数字+符号；**不同机器不复用** |
| 账号数量 | 按需最小化，测完就回收 |
| 账号命名 | 绑资产编号，方便追溯 |
| 权限 | 验证只读 sensor/sel；变更权限单独申请 |
| 协议 | 用 `-I lanplus`（v2.0）或 Redfish，不用 v1.5 |
| 网络 | BMC 口单独 VLAN，只允许跳板机访问 |
| SOL | 默认关，临时开，测完关 |

**SOL 本质上就是一条完整的 root shell 通道**，开着就得当带外登录来管。

### Redfish 比 IPMI 好在哪

| 协议 | 传输 | 说明 |
| --- | --- | --- |
| IPMI v1.5 | UDP 6233 明文 | 凭据可被嗅探 |
| IPMI v2.0 | RMCP+ | 强认证，仍建议限制访问范围 |
| **Redfish** | HTTPS | 更通用、更安全、更可审计 |

## OS 这边

### SELinux：MAC 和 DAC 的区别

传统 Linux 用用户和文件权限控制，也就是 DAC（自由访问控制）——**DAC 下 root 可以访问任何文件**。

SELinux 是 MAC（强制访问控制），给进程和文件加了一层策略约束——**MAC 下即使是 root，也只能访问策略允许的**。

排查时怀疑是 SELinux 拦的，**先查审计日志确认**：

```bash
ausearch -m AVC,USER_AVC -ts recent
getenforce
```

临时验证可以用 `setenforce 0`，**但验完必须恢复**。直接关掉 SELinux 等于拆了整道防线。

### 账号

- root 不直接 SSH（`PermitRootLogin no`）
- 日常用普通账号 + sudo
- 私钥不落在测试机上，放受控终端
- 一人一账号，人走了立刻回收
- 定期查空口令：`awk -F: '($2==""){print $1}' /etc/shadow`

### 测试环境

对联机（iperf/netperf 的 server 端）只在测试窗口开着，测完关掉。临时配的 IP（`1.1.1.1`、`2.2.2.1` 那些）不要写进网卡配置文件。

## AC Server 和 PDU

AC Server 控制着多台机器的上下电，这是**控制面**，权限要给紧。

PDU 插座号和被测机的对应关系要记准，错插就是误断别人的机器。脚本里 `-m`（PDU 名）和 `-p`（插座位置）执行前我会再核一遍。

中试部那三条我是一直守着的：不拿别人物料、自己的不放别人区域、自己区域不放别人东西。

---

## 固件

固件是跑在 OS 之下的最高权限代码，被污染了带内所有安全措施都白搭。

- 只从内部仓库取，记来源和版本
- 刷之前校验和核一遍
- 固件、驱动、OS 三者版本配套
- 固件文件权限收紧

刷固件会毁数据，动手前确认不是系统盘。

## 我自己的自查

### 交机器前

- [ ] BMC 默认账号改了或禁了
- [ ] 口令强度够，且没跟别的机器复用
- [ ] BMC 在独立 VLAN，防火墙限了来源
- [ ] 用的 lanplus / Redfish，不是 v1.5
- [ ] SOL 关了（或者有理由留着）
- [ ] BIOS 里 Trusted Computing 开了
- [ ] root 不能直接 SSH
- [ ] 没有空口令账号

### 每次动手前

- [ ] 脚本里没有明文口令
- [ ] 命令行里没有明文口令
- [ ] 固件来源和校验和确认过
- [ ] 测试网段跟办公网隔开
- [ ] PDU 插座映射再核一遍

### 日常

- [ ] 口令按周期轮换
- [ ] 人走了回收账号和证书
- [ ] 口令管理工具里的记录和实际一致
- [ ] 定期翻一遍仓库有没有漏出去的敏感信息

## 出事之后

**第一步是吊销，不是清理文件。**

1. 吊销 / 轮换那个凭据
2. 看它的访问日志，确认有没有被用
3. 清 Git 历史（大仓库用 `git filter-repo` 或 BFG）
4. 令牌的话：撤销 → 后台查活动记录 → 申请新的
5. 复盘：当初为什么会写进去
